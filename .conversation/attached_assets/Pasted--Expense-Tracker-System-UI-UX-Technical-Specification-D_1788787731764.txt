# Expense Tracker System

## UI/UX & Technical Specification

**Document Version:** 1.0
**Related Document:** 01_PRD.md
**Application Type:** Java Desktop Application
**UI Technology:** Java Swing
**Backend Services:** Supabase
**Database:** Supabase PostgreSQL
**Authentication:** Supabase Auth
**Storage:** Supabase Storage
**OCR:** Tesseract + Tess4J
**Build Tool:** Maven

---

# 1. Purpose of This Document

This document defines exactly how the Expense Tracker System should be designed, structured, implemented, and presented to the user. The purpose of this document is to remove ambiguity for AI coding agents and developers by defining the application's user interface, navigation, screen behavior, component responsibilities, application architecture, data flow, coding principles, technology restrictions, validation behavior, loading states, error states, and visual design requirements.

The AI development agent must use this document together with `01_PRD.md`. The PRD defines what the product must do, while this document defines how the product should behave and how the application should be structured. The agent must not invent major UI, architecture, or technology decisions when requirements are already defined here.

---

# 2. Non-Negotiable Technology Rules

The application must be developed as a Java desktop application.

The application frontend must use Java Swing.

Application business logic must use Java.

Supabase must be used for authentication, PostgreSQL database services, cloud storage, and Row Level Security.

OCR must use Tesseract OCR through a Java-compatible integration such as Tess4J.

Maven must be used for dependency management and project builds.

The following technologies must NOT be introduced into the project unless explicitly approved later:

* HTML
* CSS
* JavaScript
* React
* Angular
* Vue
* Python
* Node.js
* Spring Boot
* PHP
* Electron
* separate web frontend
* separate custom backend server

The application must remain a Java desktop application.

Modern visual styling may use Java Swing-compatible libraries such as FlatLaf. Charts may use JFreeChart. PDF generation may use OpenPDF.

---

# 3. Product Design Philosophy

The application should look like a modern financial desktop application rather than a default Java Swing demo.

The design should prioritize simplicity, readability, consistency, and usability. The application should use a clean layout with a persistent navigation area, modern cards, structured tables, clear buttons, meaningful icons, consistent spacing, and appropriate visual hierarchy.

The application should not attempt to imitate every feature of large enterprise expense platforms. The interface should remain focused on personal expense tracking.

The user should be able to understand the application without technical knowledge.

Every important action should provide clear visual feedback.

# 5. Navigation

The primary navigation should contain:

```text
Dashboard
Expenses
Reports
Logout
```

Additional options such as Settings or Categories should only be introduced if they are required by the implementation.

The selected navigation item should have a clear active state.

Clicking Dashboard should open the dashboard.

Clicking Expenses should open the expense management screen.

Clicking Reports should open the report screen.

Clicking Logout should ask for confirmation where appropriate and then terminate the authenticated session.

# 13. OCR User Experience

OCR must be treated as an assistant, not as an authority.

The application must never assume that OCR output is always correct.

The correct flow is:

```text
Receipt Image
     ↓
Tesseract OCR
     ↓
Raw Text
     ↓
Java Parsing
     ↓
Suggested Values
     ↓
User Verification
     ↓
Final Expense
```

The UI should visually communicate that extracted information is editable.

For example:

```text
Merchant
[ ABC Electricity Ltd. ]

Amount
[ ₹2450 ]

Date
[ 05/09/2026 ]

        ↓

Please verify extracted information.
```

The user must be able to modify every extracted field before saving.

---

# 14. OCR Fields

OCR should attempt to extract only:

```text
Merchant
Amount
Date
```

OCR should NOT automatically determine:

```text
Category
Payment Method
```

The user must select those values manually.

Example:

```text
OCR:
Merchant → ABC Electricity Ltd.
Amount   → ₹2,450
Date     → 05/09/2026

User:
Category → Utilities
Payment  → UPI
```

---

# 15. OCR Failure Behavior

OCR failure must never cause the expense workflow to fail completely.

If OCR cannot read the receipt:

```text
Unable to extract information from this receipt.

You can enter the expense details manually.
```

The application should keep the selected receipt available where possible.

The user should then be able to enter:

```text
Merchant
Amount
Date
Category
Payment Method
Description
```

manually.

---

# 16. No Receipt Workflow

Receipt upload is optional.

When the user has no receipt:

```text
Merchant
Amount
Date
Category
Payment Method
Description

Receipt:
No Receipt
```

The expense should still be saved normally.

Database representation should use something similar to:

```text
receipt_status = NO_RECEIPT
receipt_path = null
```

The application must not create a fake image or fake bill.

# 32. Error Messages

Error messages should be understandable to normal users.

Avoid displaying raw Java stack traces to users.

Instead of:


```text
Unable to save the expense.

Please check your internet connection and try again.
```

Technical details may be written to logs for debugging.

```text
+-----------------------------+
              ↓
```

Each layer must have a clear responsibility.

# 34. UI Layer

The UI layer contains Java Swing components.

Responsibilities include:

* Displaying screens
* Reading user input
* Triggering application actions
* Displaying validation errors
* Displaying success messages
* Updating tables
* Showing loading states

The UI layer must not directly contain complex database logic.

For example, a Swing button handler should not directly construct raw database requests.

Instead:

```text
Button
  ↓
ExpenseService
  ↓
ExpenseRepository
  ↓
Supabase
```

# 43. Receipt Storage Architecture

Receipt images must not be stored as binary data inside the expense database table.

The recommended architecture is:

```text
Local Receipt Image
       ↓
Java StorageService
       ↓
Supabase Storage
       ↓
Receipt Path
       ↓
Expense Database Record
```

The database should store the receipt path/reference.

Example:

```text
expense-receipts/
    user-id/
        expense-id.jpg
```

# 44. Security Architecture

Security must be enforced at the Supabase level as well as within the application.

Each expense must have a `user_id`.

Supabase Row Level Security must ensure:

```text
Authenticated User
       ↓
Can access only own expenses
```

The application must never rely only on hidden UI controls for security.

A user must not be able to access another user's data by manipulating requests.

The Supabase service-role key must never be embedded in the desktop application.

---

# 45. Threading Requirements

Swing's Event Dispatch Thread must remain responsive.

Long-running operations should not execute directly on the UI thread.

Examples include:

```text
OCR
Network requests
Receipt upload
Expense synchronization
PDF generation
Large report generation
```

Appropriate Java concurrency mechanisms should be used.

The UI should display a loading state while these operations are running.

# 62. Final Implementation Principle

The most important principle for the project is:

**Build a simple, reliable, maintainable expense tracker first and then improve its visual quality.**

The application must prioritize correct expense data, secure user isolation, reliable CRUD operations, optional receipt handling, useful OCR, accurate calculations, and dependable reporting.

Visual polish should enhance the product rather than introduce unnecessary complexity.

The AI agent must always prefer a clean and maintainable Java implementation over a complicated implementation that merely produces more visual effects or more code.
